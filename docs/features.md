# Features

What's actually implemented, not what's planned — see [ROADMAP.md](ROADMAP.md) for the feature plan and tracking issues. Update this file whenever a feature is added or its status changes.

| Feature | Status | Details |
| --- | --- | --- |
| Self-hosted server configuration | Has UI | A public server URL and an optional private (LAN) URL, with automatic switching to the private one on trusted Wi-Fi networks. Entered via `ServerSetupScreen`. See [networking-auth.md](networking-auth.md) and [app-shell.md](app-shell.md). |
| Account authentication | Has UI | Login, TOTP MFA, logout, and expiry-aware session persistence, against Trek's single-JWT session model. `LoginScreen`/`MfaScreen` wire this into the app shell; the router redirects between server setup, login, and the trip list automatically as auth state changes. See [networking-auth.md](networking-auth.md) and [app-shell.md](app-shell.md). |
| App shell (navigation, state management, design system) | Foundational, one feature screen | Riverpod + go_router + a Material 3 design system (including Trek's place category colors), a global snackbar messenger, and a reusable UI kit (empty/loading/skeleton states, cards, list rows). Trip list and trip dashboard (with Days/Places/Budget/Packing/Todos tabs) exist as placeholders; the notifications inbox is the first real feature screen. See [app-shell.md](app-shell.md). |
| App icon, splash screen & startup animation | Done | The real Trek T-mark (from the web client's source SVG) as the app icon and native launch image, plus an animated in-app splash screen styled after Trek's web login screen. See [app-shell.md](app-shell.md#app-icon-splash-image-and-startup-animation). |
| Notifications — in-app inbox | Data layer + UI | The `/notifications` screen (reached from the trip list's app-bar bell) lists the user's in-app notifications from a local cache first (instant, works offline), then refreshes from `GET /api/notifications/in-app` in the background; if that fails and nothing is cached, it shows an explicit offline/error state with a retry. Notification text is rendered client-side from a bundled English `notif.*` i18n catalog. Marking a notification read (or "Mark all read") applies locally first and syncs in the background via a pending-reads outbox, retried on the next refresh — so it works offline. No boolean yes/no responses, no delete/unread, no acting on a `navigate` target, no pagination, no live unread badge. Also adds the app's first authenticated (bearer-token) `ApiClient`. See [notifications.md](notifications.md). |
