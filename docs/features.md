# Features

What's actually implemented, not what's planned — see [ROADMAP.md](ROADMAP.md) for the feature plan and tracking issues. Update this file whenever a feature is added or its status changes.

| Feature | Status | Details |
| --- | --- | --- |
| Self-hosted server configuration | Has UI | A public server URL and an optional private (LAN) URL, with automatic switching to the private one on trusted Wi-Fi networks. Entered via `ServerSetupScreen`. See [networking-auth.md](networking-auth.md) and [app-shell.md](app-shell.md). |
| Account authentication | Has UI | Login, TOTP MFA, logout, and expiry-aware session persistence, against Trek's single-JWT session model. `LoginScreen`/`MfaScreen` wire this into the app shell; the router redirects between server setup, login, and the trip list automatically as auth state changes. See [networking-auth.md](networking-auth.md) and [app-shell.md](app-shell.md). |
| App shell (navigation, state management, design system) | Foundational, one feature screen | Riverpod + go_router + a Material 3 design system (including Trek's place category colors), a global snackbar messenger, and a reusable UI kit (empty/loading/skeleton states, cards, list rows). Trip list and trip dashboard (with Days/Places/Budget/Packing/Todos tabs) exist as placeholders. Both notifications (#15) and transit + airport search (#12) are implemented as the first real feature screens — they coexist in the app shell's app bar, each with its own dedicated screen and data layer. See [app-shell.md](app-shell.md). |
| App icon, splash screen & startup animation | Done | The real Trek T-mark (from the web client's source SVG) as the app icon and native launch image, plus an animated in-app splash screen styled after Trek's web login screen. See [app-shell.md#app-icon-splash-image-and-startup-animation](app-shell.md#app-icon-splash-image-and-startup-animation). |
| Transit & airport search | Has UI | The `/transit` screen (reached from the trip list's app-bar transit icon) does public-transit stop search, route planning between two stops, and airport lookup against `GET /api/transit/geocode`, `GET /api/transit/plan`, and `GET /api/airports/search`. Reads go through `TransitRepository`: the last results for a query paint from a local `shared_preferences` cache first, and a failed refresh falls back to that cache with an offline notice instead of blanking or throwing. Also adds the app's first authenticated (bearer-token) `ApiClient`. No departure-time picker, no transit-mode filters, and no creating an itinerary entry from a result (needs the Days feature, [#4](https://github.com/ryanmac8/trek-native-app/issues/4)). See [transit.md](transit.md). |
| Notifications — in-app inbox | Data layer + UI | The `/notifications` screen (reached from the trip list's app-bar bell) lists the user's in-app notifications from a local cache first (instant, works offline), then refreshes from `GET /api/notifications/in-app` in the background; if that fails and nothing is cached, it shows an explicit offline/error state with a retry. Notification text is rendered client-side from a bundled English `notif.*` i18n catalog. Marking a notification read (or "Mark all read") applies locally first and syncs in the background via a pending-reads outbox, retried on the next refresh — so it works offline. No boolean yes/no responses, no delete/unread, no acting on a `navigate` target, no pagination, no live unread badge. Also adds the app's first authenticated (bearer-token) `ApiClient`. See [notifications.md](notifications.md). |
| Places — place pool (read-only) | Data layer + UI | The trip dashboard's Places tab reads a trip's places from a trip-scoped local cache first (instant, works offline), then refreshes from `GET /api/trips/:tripId/places` in the background, over the app's first authenticated `ApiClient`. Each row shows the place's name, price/currency + notes, and a category badge colored from its real assigned category. Read-only so far — no create/edit/delete, category picker, or filtering to just the unassigned pool yet; and since trips (#3) aren't built yet, the dashboard itself isn't reachable from real trip data, only via its route directly. See [places.md](places.md). |
