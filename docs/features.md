# Features

What's actually implemented, not what's planned — see [ROADMAP.md](ROADMAP.md) for the feature plan and tracking issues. Update this file whenever a feature is added or its status changes.

| Feature | Status | Details |
| --- | --- | --- |
| Self-hosted server configuration | Has UI | A public server URL, plus any number of private (LAN) endpoints, each tied to one Wi-Fi network, with automatic switching to the matching endpoint when on its network. First-run onboarding (`ServerSetupScreen`) collects only the public URL; endpoints are added later from Settings → Networking (`NetworkingSettingsScreen`), which health-checks a candidate URL before saving it. See [networking-auth.md](networking-auth.md) and [app-shell.md](app-shell.md). |
| Settings hub | Has UI | A list of sub-pages (`SettingsScreen`) rather than one flat form, matching the pattern self-hosted apps like Immich use. Only "Networking" exists so far. Owns the logout action. See [app-shell.md](app-shell.md). |
| Account authentication | Has UI | Login, TOTP MFA, logout, and expiry-aware session persistence, against Trek's single-JWT session model. `LoginScreen`/`MfaScreen` wire this into the app shell; the router redirects between server setup, login, and the trip list automatically as auth state changes. A rejected token (401) no longer signs the user out — see "Sync resilience" below. See [networking-auth.md](networking-auth.md) and [app-shell.md](app-shell.md). |
| Biometric app lock | Done | Face ID / Touch ID / Android biometric unlock gates re-entry to an already-authenticated session, once per cold start. Falls back to full password re-login if biometrics fail or aren't available. See [biometric-lock.md](biometric-lock.md). |
| Sync resilience (auth failures don't block the app) | Done | An authenticated `ApiClient` now exists; a 401 flags `AuthService.needsReconnect` instead of clearing the session, and a persistent (non-blocking) banner with a "Reconnect" action shows over the trip screens instead of forcing a logout. See [networking-auth.md](networking-auth.md#authenticated-requests--sync-resilience). |
| App shell (navigation, state management, design system) | Foundational | Riverpod + go_router + a Material 3 design system (including Trek's place category colors), a global snackbar messenger, and a reusable UI kit (empty/loading/skeleton states, cards, list rows). Trip dashboard has a customizable bottom nav across nine sections (Days/Places/Budget/Packing/Todos/Book/Lists/Files/Collab); Days now reads real data, the rest are still placeholders. See [app-shell.md](app-shell.md). |
| Trip dashboard customizable nav | Has UI | Only 4 tabs fit in the collapsed bottom-nav bar at once; a trailing hamburger button slides up an overflow panel listing the rest. Any tab can be dragged between a bar slot and the panel to change which 4 show by default — the layout persists locally (`TripDashboardNavLayoutStore`, a device preference, not trip data). See [app-shell.md](app-shell.md). |
| App icon, splash screen & startup animation | Done | The real Trek T-mark (from the web client's source SVG) as the app icon and native launch image, plus an animated in-app splash screen styled after Trek's web login screen: a continuously drifting, twinkling, depth-parallaxed star field behind the T-mark reveal. See [app-shell.md](app-shell.md#app-icon-splash-image-and-startup-animation). |
| Trips — list & create | Data layer + UI | `TripListScreen` reads from a local cache first (instant, works offline) and refreshes from `GET /api/trips` in the background. A bottom `NavigationBar` splits the list into Upcoming Trips (default, sorted soonest-first) and Past Trips (sorted most-recent-first), by `Trip.endDate` vs. today. `CreateTripScreen` (`POST /api/trips`) writes new trips to that cache immediately, syncing in the background or queuing until the next refresh if offline. No edit/archive/delete/cover-image yet. See [trips.md](trips.md). |
| Days — itinerary list | Data layer + UI | The trip dashboard's Days tab reads a trip's days from a trip-scoped local cache first (instant, works offline), then refreshes from `GET /api/trips/:tripId/days` in the background. Each day shows its title (or "Day N"), date, notes, and an assignment count. Read-only so far — no day create/reorder/edit, and no place-assignment detail yet (depends on Places, below). See [days.md](days.md). |
